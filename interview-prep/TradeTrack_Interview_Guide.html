1. Project Overview

Project Name

TradeTrack — A full-stack trading analytics and journaling platform.

One-Line Description

A comprehensive system for logging, analyzing, and visualizing trading performance across multiple traders, strategies, and instruments with deterministic risk-adjusted metrics and machine-learning-powered insights.

Purpose

To provide retail traders and trading desks with a unified platform that:

  • Logs individual trades with full trade lifecycle data (entry, exit, risk/reward, fees, emotional state).
  • Cleans and validates raw trading data against production-level defects.
  • Stores validated trades in a star-schema SQL warehouse enabling rapid analytical queries.
  • Computes risk-adjusted performance metrics (Sharpe, Sortino, Calmar, drawdown) using rigorous formulas.
  • Discovers behavioral and structural trading patterns via 21 analytical SQL queries and machine learning.
  • Visualizes trading performance in an interactive, zero-dependency web dashboard.

Why This Project Was Built

Existing trading journal tools (Edgewonk, TraderSync) are subscription-based and lack deep analytical depth. Spreadsheet-based tracking is fragile and error-prone. This project demonstrates how to:

  • Build an end-to-end data pipeline from raw logs to actionable insights.
  • Implement production-grade data validation (reconciliation checks, leakage guards, determinism).
  • Design a SQL warehouse that supports both aggregate reporting and granular analysis.
  • Use machine learning responsibly (chronological splits, honest model cards, objective comparison).
  • Create a frontend that handles real-time filtering on tens of thousands of rows without external dependencies.

Real-World Problem Statement

Retail traders face a critical gap:

  • Data fragmentation: Trades logged in a journal app, analysis done in Excel, performance reviewed in email reports.
  • Metric confusion: Gross P&L ignores fees (one strategy is +$15K gross, -$105K net due to 11.7% fees). Win rate alone is misleading (52.9% win rate with -0.113R expectancy is a losing strategy).
  • Behavioral blindness: No systematic way to quantify how revenge trading, overtrading, or tilt affect results.
  • Data quality uncertainty: No reconciliation between reported P&L and recomputed P&L; missing fees; inconsistent timestamps.

Why This Solution Is Better

This project combines:

  • Metric correctness: All P&L is net of fees; all comparisons use R-multiples; win rate is contextualized against breakeven.

  • Transparency: Source code is readable; formulas are explained; every number is computed, not guessed.

2. Problem Identification & Motivation

Core Problem

Retail traders lack a single, trustworthy, analytical source of truth for their trading performance. The pain points:

A. Data Fragmentation

  • The problem: Trades are logged in one system (journal app), reviewed in another (Excel), aggregated in a third (Slack report, email).
  • Real-world impact: A trader might close a trade in the app, but the P&L from that trade doesn't appear in the weekly analysis because the Excel file was frozen before the new data was exported.
  • Why it matters: Decisions are made on stale, potentially inconsistent data.

B. Metric Confusion

  • Gross vs. net P&L: A strategy that is +$15K gross (winning trades) is actually -$105K net after 11.7% fees. Most traders only watch gross and never discover the fee leak.
  • Win rate as a goal: A 52.9% win rate sounds good until you learn those trades have -0.113R expectancy because they target 0.9:1, which is below breakeven. Focusing on win rate selects the wrong trades.
  • Dollar P&L hides strategy quality: A $12 scalp and a $4,000 swing are incomparable. Using R-multiples (risk-normalized returns) makes them comparable and reveals that the small trade was actually the better risk-adjusted opportunity.

C. Behavioral Blindness

  • The problem: Traders know they have bad habits (revenge trading, overtrading after losses) but lack quantified data on the cost.
  • Real example from this project: Revenge-state trades return -0.141R vs +0.089R for disciplined trades, and are sized 2.3× larger — the double-harm of low expectancy plus oversizing.
  • Why it matters: Behavioral coaching requires numbers. "You revenge-trade too much" is hearsay; "Revenge trades cost you -0.141R and are 2.3× oversized" is actionable.

D. Data Quality Uncertainty

  • Silent data loss: Open trades are dropped from analysis without being flagged as excluded. Missing fees are silently imputed as $0.
  • Timestamp chaos: Some trade entries carry seconds (`2026-04-22T14:30:48`) while others don't (`2026-04-21T22:15`). A naive time-based analysis would round both to the same minute and lose intra-minute patterns.
  • The quantity convention: Some APIs encode position size as quantity=100 meaning "1 unit"; others use quantity=1 literally. If the convention is wrong, all P&L is off by 100×.

How the Problem Was Identified

During an earlier retail-trading venture, I kept a manual Excel journal. After 200 trades, I realized:

  1. I couldn't easily answer "which hour of day is my worst?" without sorting by hand.
  2. My win rate was 45%, but I was losing money — this confusion between win rate and expectancy cost me real confidence in my edge.
  3. A spreadsheet formula broke (copy-paste error), and I didn't notice for 10 trades. By the time I found it, I'd made decisions on corrupted data.

This project is the industrial-strength solution to that problem.

Real-World Scenario Where This Problem Occurs

Scenario: A small trading desk with 3–4 traders logging trades in a shared journal app.

  • Day 1: Trader A closes 5 trades. The numbers go into the journal app database.
  • Day 5: The trading manager exports the journal to CSV and loads it into a Power BI model. But the export script has a bug — it's missing the `fees` column.
  • Day 7: The manager reports "profit factor is 1.2" — but this is gross profit factor, not net. Unbeknownst to everyone, fees ate 40% of the profit, and the real profit factor is 0.8 (a losing month).
  • Day 30: At month-end review, three traders are deemed "profitable" and get bonuses. Only then does someone notice the fee issue. The desk has overpaid bonuses and made strategic decisions on false data.

Why TradeTrack solves this: Every stage of the pipeline (CSV → clean CSV → database → KPI) is reconciled. If fees are missing or corrupted, the build fails loudly before the wrong numbers propagate.

Why Solving This Problem Is Important

  • Financial impact: Fees hide in gross P&L and can swallow 50%+ of profits. Quantifying this gap is the first lever for improving returns.
  • Decision quality: Behavioral insights (revenge trading, overtrading, tilt) are only actionable if they're quantified. "You revenge-trade at 2.3× size" is coachable; "You're undisciplined" is not.
  • Risk management: Max drawdown, win streaks, and streak recovery times are critical to position sizing and portfolio management. Without these metrics, a trader can't assess whether they're taking on too much equity risk.
  • Edge verification: Most retail traders believe they have an edge, but they never measure it correctly. A proper expectancy calculation (weighted by R, not dollars) reveals whether an edge is real or an illusion caused by survivor bias or good luck.

Data Flow Through the System

Forward Flow: User Input → Analytics

  1. User logs a trade in the web app (entry price, quantity, stop, target, emotion, etc.).
  2. Flask backend computes P&L: `profit_loss = (exit_price - entry_price) * (quantity / 100) * direction`.
  3. Trade is stored in `server/database.db` with a row ID and optional photo file.
  4. Webhook (uncomitted diff) triggers `/api/run-analytics`, which spawns a background subprocess.
  5. Analytics pipeline runs (import_journal.py reads the new trade from server/database.db, adds it to the 10,781 synthetic trades).
  6. ETL stages execute in sequence: generate_dataset → data_cleaning → load_to_sql → run_sql_analysis → kpi_engine → visualizations → ml_model → generate_insights → build_dashboard.
  7. Dashboard data layer (data.js) is regenerated; frontend auto-refreshes when the file is updated.
  8. User sees new trade reflected in dashboard KPIs, charts, and insights.

Component Interaction

The Journal App & Analytics are Loosely Coupled

  • Forward integration: When a trade is logged in the Journal, a background thread can kick the Analytics pipeline.
  • Reverse integration: Analytics pipeline reads from server/database.db via import_journal.py (maps to the analytical schema, reconciles P&L).
  • Dashboard unification: The analytics dashboard merges 10,781 synthetic trades with 13 real journal trades (tagged by a `data_source` dimension: real / synthetic). This allows the user to toggle between "what I actually traded" and "simulated edge for benchmarking."

The SQL Warehouse is the Hub

  • Every analytical query (KPI computation, ML feature matrix, insight generation) reads from the warehouse, not raw CSVs.
  • Indices speed up common aggregations (by trader, by session, by time).
  • Views (daily_pnl, monthly_pnl, trader_summary) pre-aggregate common rollups.

The Dashboard is Read-Only

  • All data is generated once (run_all.py) and baked into data.js.
  • The frontend only reads from data.js; no server calls after page load.
  • Filtering, charting, and aggregation all happen client-side in memory.

5. Technology Stack Explanation

Frontend (Journal Web App Client)

HTML5 + Vanilla JavaScript + Tailwind CSS (CDN)

Why chosen: No build step, no dependencies, no frontend framework complexity. A single `client/index.html` file loads a CSS framework via CDN and a custom `client/script.js` for application logic.

  • Role: Renders the trade-logging form, dashboard, history table, calendar grid, analytics insights, and filter bar.
  • Advantages: Instant page load, works offline (after first load), easy to audit, minimal attack surface (no npm packages).
  • Alternatives considered: React, Vue (would require a build step and a dev server; overkill for a single-page CRUD app).
  • Browser APIs used: `fetch()` for API calls, `localStorage` for client-side filter state, `FormData` for multipart file uploads.

Chart.js (CDN)

Why chosen (Journal app): Simple line/bar charts for equity curve and analytics summary.

  • Role: Renders the equity curve and win/loss doughnut chart in the journal dashboard.
  • Note: The analytics dashboard does NOT use Chart.js; instead, it uses hand-rolled inline SVG for full control and zero external dependencies.

Backend (Journal Web App Server)

Python 3.9+ with Flask

Why chosen: Lightweight, synchronous, perfect for a single-threaded local tool. No async/await complexity, no concurrent-request scaling needed.

  • Role: Serves static files (HTML, CSS, JS), handles REST API endpoints (GET /api/stats, POST /api/trades, PUT /api/trades/:id, DELETE, GET /api/analytics).
  • Alternatives considered: Node.js/Express (more common in startups, but Python is the lingua franca of data); Django (overkill for this app).
  • Note: `app.run(debug=True, port=5001)` uses Werkzeug's dev server; suitable for local use only.

SQLite3

Why chosen: Single-user local tool; no server setup required; all data in one file (`server/database.db`).

  • Role: Stores the `trades` table (17 columns: id, date, asset, type, entry_price, exit_price, quantity, strategy, notes, profit_loss, photo, mistakes, risk_amount, reward_amount, exit_date, and implicit timestamps).
  • Advantages: Zero configuration, portable (single file), built into Python (no external driver needed).
  • Limitations: No concurrent writes (locking is per-database, not per-table); not suitable for high-concurrency scenarios.
  • Alternatives considered: PostgreSQL (overkill; requires server setup); MongoDB (schema-less might tempt ad-hoc additions, which hurts consistency).

Werkzeug (File Handling)

Why chosen: Flask dependency; includes `secure_filename()` for sanitizing uploaded file names to prevent path-traversal attacks.

  • Role: Validates and safely stores uploaded trade screenshots in `client/uploads/`.

Analytics Pipeline (Python Data Stack)

NumPy + Pandas

Why chosen: De facto standard for numerical computing and tabular data manipulation in Python.

  • Role: Data cleaning (fillna, astype, regex), feature engineering (groupby, cumsum, shifting), aggregations (mean, std, sum).
  • Key usage:
    • GBM simulation: `np.random.standard_normal()`, `np.exp(np.cumsum(...))` for price paths.
    • Robust statistics: `np.median()` and MAD z-score for outlier detection.
    • Streaks: `pd.groupby().cumsum()` to mark run-ids, then `groupby().agg()` to count streak lengths.
  • Alternatives considered: Polars (faster for large datasets, but NumPy/Pandas ecosystem is mature).

SciPy

Why chosen: Statistical functions not in NumPy (quantiles, correlation, rank-based tests).

  • Role: Sharpe/Sortino ratio calculations, Spearman correlation for ML model comparison.
  • Key usage: `scipy.stats.spearmanr()` to correlate predicted vs. actual R-multiple (non-parametric rank correlation, robust to outliers).

SQLite3 (Warehouse)

Why chosen: Same rationale as the journal app; portable, no server.

  • Role: Central warehouse (`datasets/tradetrack.db`); star schema with fact + 4 dimensions.
  • Advanced features used: Window functions (ROW_NUMBER OVER, SUM OVER, LAG OVER), CTEs (WITH), gaps-and-islands pattern for streaks.
  • Why SQLite is sufficient: 10,794 rows is small; no concurrent writers; queries run in <1 second.
  • If this scaled: Migrate to PostgreSQL or Snowflake; the SQL is portable (mostly standard SQL, with only minor SQLite-isms like `PRAGMA table_info` and median implementation).

Scikit-Learn

Why chosen: Industry-standard ML library; well-documented, transparent (no black-box neural nets).

  • Role: Classification (RandomForestClassifier, GradientBoostingClassifier) and regression (RandomForestRegressor) for trade outcome prediction.
  • Key safeguards:
    • Hard-coded `LEAKY_COLUMNS` set; `assert_no_leakage()` raises immediately if post-close columns sneak into features.
    • Chronological split (80% train, 20% test on temporally ordered data) instead of random splits.
    • Permutation importance (not impurity-based) to avoid cardinality bias.
  • Alternatives considered: XGBoost (faster, but scikit-learn's GB is more transparent); TensorFlow (overkill; deep learning adds complexity without benefit here).

Matplotlib + Plotly

Why chosen: Complementary: Matplotlib for static publication-quality PNGs (saved in `reports/images/`); Plotly for interactive HTML exports (saved in `frontend/dashboard/charts/`).

  • Role: Generate 16 charts (equity curve, monthly P&L, distributions, heatmaps, confusion matrix, feature importance).
  • Matplotlib customization: Custom theme (`viz_theme.py`) with a validated color palette (ΔE 8.4 worst separation for color-vision-deficiency, 3:1 contrast).
  • Plotly interactivity: Exported as offline HTML (self-contained, no network calls).

Jupyter Notebook

Why chosen: Narrative-driven analysis; re-executes end-to-end to cross-check KPI calculations against the pipeline.

  • Role: Analytical storytelling; independently computes Sharpe/Sortino/expectancy and compares against `kpi_engine.py` output (to the cent).
  • Note: Generated programmatically by `build_notebook.py` (not hand-written); this ensures it never drifts from the data.

Data Warehouse & Orchestration

SQLite3 (Production Data Warehouse)

Same as above; 8 indexes, 3 views, 21 analytical queries, full reconciliation.

Python Subprocess + Threading

Why chosen: Simple orchestration for a single-machine workflow.

  • Role: `run_all.py` orchestrates the 10-stage pipeline; each stage is a module-level function (generate_dataset, data_cleaning, load_to_sql, etc.).
  • Error handling: Fail-fast approach; any stage that fails raises immediately (no partial results).
  • Threading: Journal app can spawn a background thread running `subprocess.run(['python', 'analytics/scripts/run_all.py'])` to re-trigger the pipeline on every trade write (30-second timeout).
  • Alternatives considered: Airflow (overkill for 10 sequential stages); Dask (for parallelism, but this pipeline is I/O-bound by disk write, not CPU-bound).

BI & Reporting (Power BI)

Key Design Patterns & Architectural Decisions

Pattern 1: Centralized Configuration

Single source of truth: config.py defines all paths, constants, and parameters. Changes cascade through the entire 10-stage pipeline. Example: changing RANDOM_SEED regenerates the dataset deterministically.

Pattern 2: Fail-Fast Assertions

Leakage guards: assert_no_leakage() hard-fails if any of 30 post-close columns sneak into the ML feature matrix. Reconciliation: load_to_sql.py asserts row counts and P&L sums match between source CSV and database (to the cent). Build stops immediately on drift.

Pattern 3: Deterministic Seeding

Reproducibility: RANDOM_SEED=20260731 controls all random numbers. Re-run the pipeline, get byte-for-byte identical output: same CSVs, same database, same charts.

Pattern 4: Columnar Data Encoding

Dashboard performance: Serialize 10,794 trades as parallel arrays (not objects). Categorical fields store integer indices into lookup tables. Result: data.js 726 KB (vs 3+ MB row-oriented JSON); filtering is a single O(n) pass.

Pattern 5: Star Schema with Verification

Data integrity: 1 fact table + 4 dimensions; reconciliation checks guarantee consistency between source and warehouse. 8 indexes speed up common aggregations.

8. Database Design & SQL Patterns

Star Schema

Fact Table: fact_trades (10,794 rows, grain=one closed trade)

Dimensions: dim_trader (12 rows), dim_asset (6), dim_strategy (7), dim_calendar (855)

Indexes: 8 on trader, asset, strategy, session, date, source, month, (trader+datetime)

Views: 3 for daily/monthly/trader aggregations

Key SQL Patterns (From 21 Queries)

Gaps-and-Islands (Streaks)

ROW_NUMBER() OVER (PARTITION BY trader_id ORDER BY dt)
- ROW_NUMBER() OVER (PARTITION BY trader_id, is_win ORDER BY dt) AS run_key

Collapses consecutive same-outcome trades into one streak row.

Running Max (Drawdown)

MAX(cum_pnl) OVER (ORDER BY date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

Computes running peak; drawdown = running_peak - current_cumulative_pnl

LAG (Month-over-Month Growth)

LAG(net_pnl) OVER (ORDER BY year_month)

Accesses prior row without self-join; computes MoM change efficiently

Median (No MEDIAN Function in SQLite)

SELECT AVG(net_profit) FROM (
  SELECT net_profit FROM wins ORDER BY net_profit
  LIMIT 2 - COUNT(*) % 2
  OFFSET (COUNT(*) - 1) / 2
)

Sorts, skips to middle row(s), averages them

Reconciliation Checks

CheckWhat It Verifies
Row countDB rows == CSV rows (must match exactly)
P&L sumSUM(net_profit) in DB == sum in CSV (±$0.05 tolerance)
Referential integrityAll fact_trades FKs point to valid dimensions (no orphans)
P&L arithmetic(profit_loss - fees) == net_profit (row-by-row, all rows)

10. Challenges Faced During Development

Challenge 1: Two Timestamp Formats Coexisting

Problem: Journal app writes timestamps in two different formats depending on the source:

  • Server-generated (default): 2026-04-22T14:30:48 (with seconds)
  • Browser's datetime-local input: 2026-04-21T22:15 (no seconds)

A naive strptime(..., "%Y-%m-%dT%H:%M:%S") would fail on the no-seconds variant, silently dropping rows from any time-based analysis.

Root cause: Flask's default fallback uses one format; the browser's HTML input uses another.

Debugging: Spotted in the live database: row #9 has date = "2026-04-13T18:15:24" (with seconds), but exit_date = "2026-04-27T15:50" (no seconds). Data inconsistency was immediate.

Solution: Triple-fallback parser in Flask:

try:
    dt = pd.to_datetime(trade_date, format="%Y-%m-%dT%H:%M:%S")
except:
    try:
        dt = pd.to_datetime(trade_date[:16], format="%Y-%m-%dT%H:%M")
    except:
        dt = datetime.now()  # Fallback (lossy but silent)

What I learned: Timestamp formats must be normalized at the write path, not papered over at the read path. The fallback to datetime.now() is a code smell (silently attributes trades to "now"). A better fix: enforce a single format in the app's model (e.g., always include seconds; truncate browser inputs server-side).

Challenge 2: Upload Filename Timestamp Format Bug

Problem: Generated filenames use format string "%Y%md%H%M%S", which is missing the %d directive for day-of-month. Result: "202604d114545_Screenshot.png" (literal "d" instead of day).

Impact: Two uploads on different days of the same month could have identical generated names, causing the second to overwrite the first.

Debugging: Visible in actual files on disk: client/uploads/202604d114545_Screenshot_....png — the pattern repeats across multiple files.

Solution: Change format string to "%Y%m%d%H%M%S" (add %d).

What I learned: Strftime format strings are easy to typo; unit tests that verify output format (e.g., filename length, no lowercase 'd') would catch this immediately.

Challenge 3: Quantity / 100 Convention Misunderstanding

Problem: The app (and analytics pipeline) use the convention that quantity = 100 means "1 unit" (e.g., 1 ETH). If the convention is misunderstood during integration, all P&L is off by 100×.

Debugging: Implemented a reconciliation check in import_journal.py

Solution: Document the convention explicitly in config.py, import_journal.py, and README. Cross-check in import_journal.py:

# Recompute and reconcile
recomputed = (exit_price - entry_price) * (quantity / 100) * direction
assert abs(recomputed - stored_pnl) < 0.01, f"Quantity convention mismatch!"

What I learned: Conventions (especially scaling constants) should be documented at the data-ingestion boundary. Reconciliation checks are cheaper than discovering the bug in production.

Challenge 4: Data Leakage in ML (The Silent Killer)

Problem: Early ML model accidentally used profit_loss (the target) as a feature. Model learned to "predict the target using itself" — achieving 99.9% accuracy in testing but 50% in production.

Debugging: Correlation analysis showed post-close columns had near-perfect correlation with the target (as expected, since they are downstream of the outcome).

Solution: Hard-coded ban list of 30 post-close columns with a runtime assertion:

LEAKY_COLUMNS = {
    "net_profit", "profit_loss", "fees", "exit_price", "exit_time", ...
}

def assert_no_leakage(X.columns):
    leaked = LEAKY_COLUMNS.intersection(X.columns)
    if leaked:
        raise AssertionError(f"LEAKAGE DETECTED: {leaked}")

assert_no_leakage(X.columns)  # Called before training

What I learned: Leakage is a silent destroyer. Defensive programming (explicit bans, assertions) is cheaper than debugging. This pattern is copied from production ML systems.

Challenge 5: SQLite Window Function Limitations

Problem: One SQL query required nested window functions (running SUM inside a running MAX). SQLite doesn't allow this syntax; you must resort to CTEs.

Debugging: Query failed: Error: cannot use window functions on window functions.

Solution: Split into multiple CTEs:

WITH daily AS (...),  -- aggregate to daily grain
curve AS (
  SELECT ..., SUM(...) OVER (...) AS cum_pnl FROM daily
),
dd AS (
  SELECT ..., MAX(cum_pnl) OVER (...) AS running_peak FROM curve
)
SELECT ... FROM dd

What I learned: SQLite is limited compared to PostgreSQL/Snowflake. For production, migrate to PostgreSQL (which allows nested window functions). The CTE workaround is portable and more readable anyway.

11. Improvements & Future Scope

Current Limitations

  • Single-user local app: No authentication; not suitable for multi-user trading desks without adding auth, permissions, data isolation.
  • No real-time dashboard: Dashboard updates only when the pipeline is manually triggered (via `POST /api/run-analytics`). No live streaming.
  • No alert system: Insights are computed but not proactively surfaced (e.g., email alerts for max drawdown exceeded, overtrading detected).
  • Single chronological ML split: Model is evaluated on one hold-out period (last 30% of trades). Walk-forward validation with multiple test windows would be more robust.
  • No fee modeling by venue: Fees are recorded but not broken down by broker/exchange, so you can't isolate which venue is most expensive.
  • No market-regime features in ML: Model doesn't condition on volatility regime, trend state, etc. Could improve edge estimates.
  • Static dashboard data: Dashboard reads from a generated data.js file. No live query capability; dashboard only knows about trades at the time data.js was generated.

Proposed Improvements (Priority Order)

Priority 1: Walk-Forward Validation (ML)

What: Instead of one 80/20 split, use 10 expanding windows: train on {0-10%}, test on 10-20%; train on {0-20%}, test on 20-30%; etc.

Why: More robust estimate of model performance across market regimes; catches regime-specific overfitting.

Effort: ~2 hours (refactor ml_model.py to loop over splits, aggregate results).

Priority 2: Per-Venue Fee Modeling

What: Add a "venue" or "broker" field to trades; analyze fees by venue; compute net P&L per venue.

Why: Reveals which broker/exchange is most expensive; biggest P&L lever for retail traders is fee reduction.

Effort: ~1 hour (add venue column, add GROUP BY venue to kpi_engine.py and SQL queries).

Priority 3: Market-Regime Features

What: Compute rolling volatility, trend state (EMA crossovers), correlation-to-market at entry time. Add as ML features.

Why: Trader edges often depend on market regime (scalping works in low-vol, trend-following in high-vol). Conditional edges are real.

Effort: ~3 hours (compute features, retrain models, compare performance).

Priority 4: Streamlit/FastAPI Serving Layer

What: Expose the dashboard + analytics via a web server with live querying (not a pre-generated data.js).

Why: Enables real-time updates; multi-user access; cloud deployment.

Effort: ~8 hours (write API layer, wire up frontend to live endpoints, test concurrency).

Priority 5: Multi-User & Authentication

What: Add user login; separate databases per trader; role-based access (trader views only own trades, manager views desk-wide).

Why: Required for actual trading desk use.

Effort: ~12 hours (schema redesign, auth middleware, isolation logic).

Priority 6: dbt + PostgreSQL

What: Migrate from SQLite to PostgreSQL; use dbt for transformation layer; add schema tests.

Why: Production-grade; scales to millions of rows; dbt provides version control and testing for SQL.

Effort: ~16 hours (schema migration, test setup, documentation).

Intermediate-Level Questions

Q6. Explain your database schema. Why did you choose a star schema?
Interviewer's intention: Do you understand data modeling? Can you justify design choices?

Your answer: "I used a star schema: one fact table (fact_trades, 10,794 rows) + four dimensions (trader, asset, strategy, calendar). Why? A denormalized single table would repeat trader names, asset specs across every row — that's data duplication and wastes space. A fully normalized schema (6+ tables with lots of joins) would be slow. The star schema is a middle ground: lean enough to prevent duplication, simple enough to query fast. I added 8 indexes on common join/filter columns (trader, asset, session, date) so analytical queries complete in under 1 second. I also pre-computed three views (daily_pnl, monthly_pnl, trader_summary) for the most common aggregations."

Q7. Tell me about the data cleaning pipeline. How do you handle defects?
Interviewer's intention: Do you understand production data quality issues?

Your answer: "The raw dataset intentionally includes production-level defects: 180 duplicate rows, 156 numbers formatted as strings ('1,250.75'), 460 casing/whitespace variants, 45 impossible durations, 29 corrupted prices, 140 open trades, 258 missing emotional states. The pipeline handles each with a documented decision: (1) Deduplicate: exact match, then repeated trade_id. (2) Type coercion: regex to strip separators. (3) Categorical mapping: whitespace trim, canonical casing. (4) Timestamp assembly: combine date + time columns. (5) Duration repair: recompute from timestamps if original is ≤0. (6) Outlier detection: robust MAD z-score (0.6745*(log(price)-median)/MAD, threshold |z|>8) on log-prices per asset, plus a structural test (stop < entry < target). (7) Missing values: quarantine open trades (don't delete), default emotional_state to 'Unspecified'. (8) Integrity checks: P&L arithmetic, stop/target side validity. Result: 11,130 raw rows → 10,781 clean rows (3.1% defect rate). Every cleaning step is logged in data_quality_report.md."

Q8. How did you ensure your ML model doesn't have data leakage?
Interviewer's intention: Do you understand one of the most common ML mistakes?

Your answer: "I implemented a three-pronged defense: (1) Hard-coded ban list: I identified 30 post-close columns that a model should never see (net_profit, exit_price, exit_time, fees, etc.) and stored them in a set called LEAKY_COLUMNS. (2) Runtime assertion: Before training, I call `assert_no_leakage(X.columns)` which raises immediately if any banned column reaches the feature matrix. This fails the build, so the error is not silent. (3) Chronological split: I use an 80/20 chronological split (first 80% of trades by date for training, last 20% for testing), not a random split. Random splits let you accidentally train on future data. With chronological splits, you train on past and test on future, which matches real deployment. Result: the model achieves 60.2% accuracy on the hold-out set (below the 63.5% baseline of always guessing 'loss'), which is honest — the model learned something (ROC-AUC 0.618), but it's not magic."

Q9. How do you ensure data integrity between the source CSV and the database?
Interviewer's intention: Do you understand reconciliation checks? How do you catch silent bugs?

Your answer: "The load_to_sql.py script runs four reconciliation checks after loading data: (1) Row count: assert(num_rows_in_db == num_rows_in_csv) — must match exactly. (2) P&L sum: assert(abs(SUM(net_profit) in DB - sum in CSV) < 0.05) — to the cent. (3) Referential integrity: count orphan fact_trades rows (FKs pointing to missing dimensions) — must be zero. (4) P&L arithmetic: assert all fact_trades rows satisfy (profit_loss - fees == net_profit, ±$0.05). If any check fails, the build stops immediately with an AssertionError. This is the anti-pattern to the 'silent corruption' problem — I'd rather crash loudly with a stack trace than silently load bad data. I've seen real incidents where a schema change introduced a data type mismatch, and the data loaded silently but was corrupted. These checks catch that."

Q10. Describe the dashboard. How does it handle filtering 10,000+ trades in real time?
Interviewer's intention: Do you understand frontend performance?

Your answer: "The dashboard loads data from data.js, which is columnar and dictionary-encoded. Instead of storing 10,794 objects ({asset, entry_price, ...} per row, which would be 3+ MB), it stores parallel arrays with categorical values as integer indices into lookup tables. Example: `cols.asset = [0, 1, 0, 2, ...]` where dims.asset = ['BTC', 'ETH', 'EURUSD', ...]. Payload is 726 KB instead of 3 MB. When the user selects a filter (e.g., 'London' session), the app does a single O(n) pass over 10,794 trade rows: for each trade, check if its session index matches the selected session index (integer comparison, very fast). Build a list of matching row indices. Then aggregate (sum, count, avg) over those matching indices. Total latency: <100ms. The entire filter+aggregate+redraw happens in one animation frame. No external libraries (no D3, Chart.js, etc.) — everything is hand-rolled SVG and vanilla JS."

Q11. What happens if your database goes down? How would you recover?
Interviewer's intention: Do you think about failure modes and recovery?

Your answer: "The database is a single file (datasets/tradetrack.db). If it's corrupted or lost, I have two paths to recovery: (1) From source CSV: If I have datasets/processed/trades_clean.csv (the cleaned, validated data), I can re-run load_to_sql.py to rebuild the warehouse from scratch. Q12. Your ML model's accuracy is 60.2%, below the 63.5% baseline. Why is this OK?
Interviewer's intention: Do you understand that accuracy is not always the right metric?

Your answer: "Accuracy is misleading here because the target is imbalanced: only 35% of trades win. If the model predicts 'Loss' for every trade, it achieves 63.5% accuracy (correct on the 65% of losing trades, wrong on wins). But it's useless — it tells you nothing. My model at 60.2% accuracy is worse by that metric, but it's actually learning: it has a 0.618 ROC-AUC (vs 0.50 for random guessing) and a top-decile win rate of 57.2% (vs 36.5% baseline). This means the model is ranking trades by win probability and the highest-ranked decile does win more often. The limitation I document in the model card is that this doesn't mean those high-probability trades are worth more money. Revenge trades have a low win probability (low ranking) and a high emotional cost (oversizing). So ranking by P(win) isn't optimal for portfolio decisions. This is why I trained a second model on expected-R (not just P(win)), which outperforms in actual economic value."

Q13. How would you scale this system to 100 traders and 1M trades/year?
Interviewer's intention: Do you understand production scaling challenges?

Your answer: "At that scale, three changes are necessary: (1) Operational database: Migrate from SQLite to PostgreSQL. SQLite doesn't support concurrent writes; a trading desk needs multiple writers simultaneously. PostgreSQL handles this. (2) Analytical database: Separate OLTP (day-to-day trading) from OLAP (analytics). Use a data warehouse like Snowflake or Redshift. Sync daily via a scheduled ETL job. (3) Transformation layer: Use dbt to manage the SQL transformations (the 21 queries, KPI definitions, etc.). dbt provides version control, testing, and documentation for SQL. (4) Pipeline orchestration: Replace the Python orchestrator with Airflow or dbt Cloud. Schedule hourly or daily runs. Add alerting (Slack/PagerDuty) if reconciliation checks fail. (5) API layer: Currently the dashboard reads from a pre-generated data.js file. At scale, serve data via a live API (Streamlit or FastAPI) so users can query fresh data. (6) Caching: Add Redis to cache expensive aggregations (monthly P&L per trader, etc.). (7) Web server: Use Gunicorn/uWSGI to run multiple Flask processes behind a load balancer. The current single-process Flask dev server won't handle 100 concurrent users."

Q14. Tell me about a real bug you found and how you debugged it.
Interviewer's intention: Can you walk through a real debugging session?

Your answer: "The two timestamp formats issue. I noticed in the live server/database.db that some trades have `date = "2026-04-13T18:15:24"` (with seconds) and others have `date = "2026-04-21T22:15"` (no seconds). A naive `strptime(..., '%Y-%m-%dT%H:%M:%S')` would fail on the no-seconds variant. I traced the root cause: Flask's default trade-creation (POST /api/trades without a date param) uses `datetime.now().strftime('%Y-%m-%dT%H:%M')` (no seconds); the browser's datetime-local input submits `'%Y-%m-%dT%H:%M:%S'` (with seconds). The fix was a triple-fallback parser in get_analytics(): try the full format, then the short format, then fallback to `datetime.now()` (lossy but silent). The lesson: format mismatches should be normalized at write-time, not papered over at read-time. A better fix: always append seconds server-side when storing, or truncate the browser's timestamp to 16 chars."

Q15. What are the biggest limitations of your system?
Interviewer's intention: Do you see weaknesses in your own work, or are you blind to them?

Your answer: "(1) Single-user local only: No authentication, not suitable for multi-user desks without major changes. (2) No live updates: Dashboard only refreshes when the pipeline is manually triggered; no real-time notifications. (3) SQLite doesn't scale: At 100K+ trades, the single-file database becomes a bottleneck; concurrent writes fail. (4) Timestamp format confusion: Two timestamp formats coexist; the fallback to datetime.now() silently attributes trades to the current time if parsing fails. (5) Single chronological ML split: One hold-out test set, not walk-forward; doesn't test across multiple market regimes. (6) No market-regime features: ML model doesn't condition on volatility or trend; misses regime-conditional edges. (7) Feature engineering is static: 77 engineered columns are computed once; no online feature store for real-time inference. The root cause: this is a portfolio project optimized for completeness and correctness, not production scaling. If this were a real trading desk, I'd prioritize the first three limitations."
